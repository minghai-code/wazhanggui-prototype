## 0. 模块通用说明（7 页共用）

### 0.1 这个模块解决什么问题

物业维修是"看不见的黑箱"：报修靠电话、采购靠口头、发票事后补。
**一年 30 万维修资金花在哪、单价是否合理、有没有重复报修、商户整改是否落地，全是糊涂账。**

本模块把四条业务线拆开、各自闭环，并让单据之间互相咬合：

| 线 | 链路 | 落到哪页 |
|---|---|---|
| ① **报修与维修资金**（主干，监管核心） | 报修 → 派单 → 处理 → **判定是否需采购（标记，仍留在处理中）** → 攒批建**交办单** → 审批链 → 逐行**核销** → 回报修单转待确认 → 年度**额度**扣减 | P1 报修工单 / P2 交办单与核销 / P3 维修资金台账 |
| ② **现场治理** | 巡检计划 → 任务 → 发现问题 → 按**责任方**分流（商户→整改 / 物业→报修） | P5 巡检 / P6 问题 / P7 整改 |
| ③ **投诉建议** | 受理 → 回复 → 转单反哺（维修质量→报修、秩序问题→整改） | P8 投诉 |
| ④ 保洁管理 | 与 ② 同构，**本期只定义不做原型**（菜单占位 `dev`） | — |

> **不得混线**：报修单（`BX`）只由 P1 生成；交办单（`JB`）只由 P2 生成；整改单（`ZG`）只由 P6/P7 生成。**P6 转报修是"新建 BX + 原 WT 记录保留"，不是把 WT 改名为 BX。**

### 0.4 审批链（金额分档，系统判定）

| 金额 | 链长 | 节点（串行） |
|---|---|---|
| **< 1,000 元** | 2 级 | 市场管理部 → 市场部负责人 |
| **≥ 1,000 元** | 4 级 | 市场管理部 → 市场部负责人 → 分管领导 → 董事长 |

> **档位由金额自动计算，提交人无法选择**。驳回后版本号 +1，重提**从第一级重新审批**。

### 0.5 硬校验 vs 标异常（本模块最容易搞错的地方）

| 类别 | 场景 | 处理 |
|---|---|---|
| **硬拦（不通过）** | 要素不全、未勾物资行、**发票号重复**、照片缺失/复用 | 直接拦截 |
| **标异常（放行但记账）** | 数量超核、单价超审批 10%、累计金额超审批、换供应商 | 核销成功，同时生成 `YC` 异常，进异常台账待处置 |
| **额度不足** | 剩余额度 < 本次核销金额 | **阻断核销**，提示跳 P3 申请追加 |

> **为什么不全拦**：采购现场存在合理偏差（涨价、多买）。全拦会让一线绕过系统；全放又失去监管。**放行 + 记账 + 必须处置**才是可执行的。

## 1. 页面定位

**P1 报修工单**是四条线的入口。照片是核心凭证（**上报与处理前后都要**），状态决定谁该做什么。

- 使用者：物业专员（受理/派单/处理）、物业主管（驳回/改派）
- 上游：商户端 App 报修、物业巡逻上报、问题上报转报修（**巡检模块已下线，「巡检转单」来源已移除**，历史单据并入「问题上报转单」）
- 下游：**需采购（打标记，单据留在处理中）→ P2 建交办单核销 → 回本页转待确认**；无需物料 → 待确认 → 商户确认/3 天自动完成

## 3. 统计卡口径

| 卡 | 口径 |
|---|---|
| 待受理 | `state = 待受理` |
| 处理中 | `state ∈ {已派单, 处理中}`（两态合并计一个 Tab） |
| 需采购（v1.9） | `needMat = true` 且 `state ∈ {已派单, 处理中}`，即已判定需采购、尚未核销转待确认的单；**原独立「待采购」状态已取消** |
| 待确认 | `state = 待确认`（已提交结果，等商户确认或 3 天自动确认） |
| 本月已完成 | `state = 已完成` |

> **超时基线**：待受理 > **2 小时**；需采购未核销 > **30 天**（`needMat=true && state=处理中 && 停留时长 > 720 小时`）。命中即标红「超时」。

## 4. 状态机（6 态）

> **v1.9 变更**：原「待采购」不再是报修单状态。提交结果判「需采购」时，单据**留在「处理中」**并打 `needMat` 标记；采购由 P2 交办单与核销页承接，核销完成后回本页点「核销完成 · 转待确认」。

```mermaid
stateDiagram-v2
    [*] --> 待受理: 商户端提交 / 巡逻上报
    待受理 --> 已派单: 受理并派单（指定维修工 + 预计到场）
    待受理 --> 已驳回: 驳回（原因必填，通知报修人）
    已派单 --> 处理中: 维修工到场
    处理中 --> 待确认: 提交结果（无需物料 + 处理后照片）
    处理中 --> 处理中: 提交结果判定需采购 → 标记 needMat（状态不变）
    处理中 --> 待确认: 交办单物料核销完成（核销完成 · 转待确认）
    待确认 --> 已完成: 商户确认 / 超 3 天自动确认
    待确认 --> 处理中: 商户退回「未修好」
```

### 6.1 核销完成自动回写（v2.0 · 2026-11-18）

> 原设计靠 P2「待采购 → 待确认（由交办单驱动）」，但两页数据不打通，实际变成了 P1 一个「核销完成 · 转待确认」按钮——等于让运营在看不到核销进度的情况下人工确认一次，**已废弃**。

| 项 | 口径 |
|---|---|
| 触发方 | P2「交办单与核销」页 `doEntry()`：本次核销后 `allDone = 全部物资行 done ≥ qty` |
| 前置门槛 | 该交办单**无「待处置」异常**（有异常先处置完，不自动转） |
| 动作 | 写 `localStorage.wuye_bx_confirm`（key = 报修单号，值 = `{jb, at}`）；P1 加载时 `applyBackConfirms()` 读取并把 `处理中 → 待确认`，时间轴补「交办单 JBxxx 核销完成（系统自动）」 |
| 部分核销 | **不触发**，单据留在处理中。列表**不展示核销件数进度**——核销是按交办单物资行做的，不落到某一台报修单上，展示 x/y 属于伪精度 |
| 一单多报修 | 交办单 `bx[]` 里每条逐条回写，一条不落 |
| P1 界面 | 列表操作列**不再有**「核销完成 · 转待确认」；详情「物料需求」块只展示「是否需要采购 = 是」+ 关联交办单，**不展示核销件数进度**（核销按物资行做，不落到单张报修单） |
| 异常兜底 | 交办单作废、走售后、物料由商户自备等：详情抽屉内「强制转待确认（异常路径）」灰链，**必须填原因**，日志标「【强制】」 |
