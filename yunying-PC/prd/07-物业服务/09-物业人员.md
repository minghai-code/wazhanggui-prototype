## 1. 页面定位

给"派单给人"提供**人的目录**——只管业务属性，不管账号。

- 使用者：物业主管（维护档案）、袜业城运营
- 上游：统一用户体系（账号来源，本页**只读**）
- 下游：`property-repair.html` 派单候选、`property-issue.html` 问题处置人、移动端 `wuye-home.html` 身份判定
- **已下线（2026-11-03）**：巡检管理、整改管理（含复核人分配）；巡检员/保洁岗位仅保留档案属性，不再派单

**为什么单独一页（不塞进统一账号管理）**

| 理由 | 说明 |
|---|---|
| 账号归统一用户体系 | 建号、密码、启停、角色授予都在那边；本页用 `userId` 关联，**不建账号、不改密码** |
| 业务属性是本模块专属 | 岗位 / 负责区域 / 在岗状态 / 上级主管，塞进账号表会污染通用模型 |
| 离职是业务事件 | 账号停用一键即可，但**名下未完成单必须转派**——只有业务模块知道什么叫报修单、巡检任务 |
| 数据权限与考核依赖它 | R-43 按区域收窄可见范围；工作量与响应时长按人统计 |

## 2. 分区结构

无 Tab，单页两段。

**统计卡（5）**：在岗人员 · 休假 · 停用 · 名下未完成单 · 未配上级

> 「未配上级」= 非主管岗位且上级为空的人数，用于暴露 ST-1 数据质量漏洞（无上级 → 超时无人兜底）。
> 「名下未完成单」只统计**非停用**人员，停用人员的单必须为 0（否则说明转派没做完）。

**工具条**：关键词（姓名 / 手机号 / 负责区域，实时过滤）+ 岗位 + 在岗状态 + 重置
**列表**：`人员清单 共 N 人` + 全选复选框

## 5. 在岗状态与停用

| 动作 | 条件 | 效果 |
|---|---|---|
| 设为休假 | 在岗 | 停止新派单，**已派单不撤回** |
| 恢复在岗 | 休假 | 重新进入派单候选 |
| **停用** | 任意 | 有未完成单时**必须先转派**，逐类展示待转派单据（报修 / 巡检）；无单可直接停用 |
| 启用 | 停用 | 恢复在岗，重新接单 |

**停用弹层规格**

1. 顶部：姓名 + 工号 + 「名下还有 N 张未完成单」
2. 待转派清单：**条数与 `名下未完成单` 严格一致**，逐条显示类型 + 单号 + 摘要 + 当前状态
3. 接手人下拉：**在岗 + 岗位有交集**的人员（巡检员的巡检任务不能转给纯维修工）；显示「姓名（岗位 · 区域）」
4. 无合格接手人时：不出现下拉，改为警示块「当前没有在岗且岗位匹配的人员可接手……否则 N 张单会失去责任人」，并**阻断停用**
5. 转派范围：接手的只有**报修单**（巡检与整改已下线，其历史单据不再产生新的转派需求）

**规则**

| 编号 | 规则 |
|---|---|
| ST-1 | 一个账号只能有一条物业人员档案 |
| ST-2 | 停用必须完成转派，未完成单不允许挂空 |
| ST-3 | 岗位含「主管」才可派单 / 改派 / 责任方判定 / 整改复核（见 `01-报修工单.md` §0.3） |
| ST-4 | 区域变更与停用全部留痕（原值 → 新值 + 操作人 + 时间） |
| ST-5 | 保洁本期只建档案不派任务（保洁模块占位） |

## 7. 端间协同落点

| 数据 / 动作 | 本页（PC，唯一主权） | 另一端 | 可见条件 |
|---|---|---|---|
| 岗位 / 负责区域 / 在岗状态 | **维护方** | `wuye-home.html` / `wuye-mine.html` 身份与排班展示 | 档案启用且岗位匹配 |
| 在岗状态 = 休假 / 停用 | 维护方 | 移动端「物业管理」入口消失、不在派单候选 | ST-2 转派完成后生效 |
| 停用转派 | 维护方（强制） | 巡检/报修任务改派，移动端「我的单」刷新 | 目标任务已转派 |
| 未完成单数 | 汇总展示 | 只统计**报修单**（`wuye-repair.html`）；巡检与整改已下线，不再产生新单 | 仅非停用人员统计 |
| 工作量化（响应时长 / 完成量） | 汇总展示（本期仅计数） | 移动端产生 | 二期出报表 |

> 本页**不写**任何资金数据（R-46）；移动端也不需要人员档案的维护入口（PC 独占）。
