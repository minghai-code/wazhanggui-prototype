0. 模块通用说明（7 页共用）

0.1 这个模块解决什么问题

物业维修是"看不见的黑箱"：报修靠电话、采购靠口头、发票事后补。 一年 30 万维修资金花在哪、单价是否合理、有没有重复报修、商户整改是否落地，全是糊涂账。

本模块把四条业务线拆开、各自闭环，并让单据之间互相咬合：

线链路落到哪页
① 报修与维修资金（主干，监管核心）报修 → 派单 → 处理 → 需物料则进待采购池 → 攒批建交办单 → 审批链 → 逐行核销 → 年度额度扣减P1 报修工单 / P2 交办单与核销 / P3 维修资金台账
② 现场治理巡检计划 → 任务 → 发现问题 → 按责任方分流（商户→整改 / 物业→报修）P5 巡检 / P6 问题 / P7 整改
③ 投诉建议受理 → 回复 → 转单反哺（维修质量→报修、秩序问题→整改）P8 投诉
④ 保洁管理与 ② 同构，本期只定义不做原型（菜单占位 dev）—
不得混线：报修单（BX）只由 P1 生成；交办单（JB）只由 P2 生成；整改单（ZG）只由 P6/P7 生成。P6 转报修是"新建 BX + 原 WT 记录保留"，不是把 WT 改名为 BX。

0.5 硬校验 vs 标异常（本模块最容易搞错的地方）

类别场景处理
硬拦（不通过）要素不全、未勾物资行、发票号重复、照片缺失/复用直接拦截
标异常（放行但记账）数量超核、单价超审批 10%、累计金额超审批、换供应商核销成功，同时生成 YC 异常，进异常台账待处置
额度不足剩余额度 < 本次核销金额阻断核销，提示跳 P3 申请追加
为什么不全拦：采购现场存在合理偏差（涨价、多买）。全拦会让一线绕过系统；全放又失去监管。放行 + 记账 + 必须处置才是可执行的。

1. 页面定位

P1 报修工单是四条线的入口。照片是核心凭证（上报与处理前后都要），状态决定谁该做什么。

  • 使用者：物业专员（受理/派单/处理）、物业主管（驳回/改派）
  • 上游：商户端 App 报修、物业巡逻上报、（可选）巡检问题转报修
  • 下游：需物料 → P2 待采购池；无需物料 → 待确认 → 商户确认/3 天自动完成

超时基线：待受理 > 2 小时；待采购 > 30 天未核销。命中即标红「超时」。
